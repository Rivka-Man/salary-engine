# מנוע חישוב גמול השתלמות — עוז לתמורה

## מה יש כאן

| קובץ | תפקיד |
|---|---|
| `schema.sql` | סכמת ה-DB (PostgreSQL): טבלת חוקים, פרמטרים, מורים, קורסים, סטטוס תעסוקתי, תוצאות חישוב |
| `db.py` | חיבור משותף ל-DB (Postgres/Supabase), בשימוש ע"י `engine.py` ו-`app.py` |
| `engine.py` | הליבה: זריעת טבלת החוקים + פונקציית `compute_gimul_hishtalmut()` שמריצה את כל 18 החוקים |
| `app.py` | ממשק הווב (Flask) — ניהול מורים, קורסים, סטטוס תעסוקתי, קישורים אישיים |
| `example_run.py` | דוגמה מלאה מקצה לקצה — מזין מורה לדוגמה, מריץ את המנוע, מדפיס תוצאה + trace |
| `example_output.json` | פלט החישוב המלא של הדוגמה, כולל ה-audit trail |
| `db.env` | (לא ב-git) — `DATABASE_URL` של ה-DB בפועל, ראו "התקנה" למטה |

## איך זה בנוי (הארכיטקטורה)

```
┌─────────────────┐    ┌───────────────────────┐
│   טבלת rules    │    │  טבלת rule_parameters  │  ← "מה ולמה" (מקור, סעיף) +
│   (ב-DB)         │    │  (ב-DB)                 │    "כמה" (שעות ליחידה, תקרות,
└────────┬─────────┘    └──────────┬──────────────┘    אחוזים) לפי rule_id + תוקף
         │ rule_id                  │ rule_id + calc_date
         └────────────┬─────────────┘
              ┌────────▼─────────┐
              │  engine.py        │  ← הלוגיקה בפועל: איזה חוק/ערך חל על מי,
              │  (compute_...)    │     ממומשת כקוד פייתון, בונה trace
              └────────┬─────────┘
                        │
              ┌─────────▼─────────┐
              │  teachers /        │  ← נתוני קלט: מורה, קורסים, סטטוס תעסוקה שנתי
              │  courses / ...     │
              └─────────┬─────────┘
                        │
              ┌─────────▼─────────┐
              │  calculation_runs │  ← כל הרצה נשמרת: תוצאה + JSON מלא של ה-trace (audit)
              └───────────────────┘
```

**למה החוקים לא "ב-DB" באמת (כנוסחה שרצה מ-SQL)?**
כי חוקים כמו "אם שבתון אז בלי תקרה שנתית, אחרת תקרה 1 עם carry" הם לוגיקה מדורגת עם תלות בין שנים — קשה וחסר-אמינות לייצג כמחרוזת שרצה דינמית (`eval`), וקל מאוד לפצח כקוד רגיל, קריא, וניתן לבדיקה (unit tests). ה-DB שומר את ה"מה ולמה" (metadata, תיעוד, סעיפים), הקוד מבצע את ה"איך".

**אז מה כן בטבלה?** ה**ערכים הסופיים** של החוקים (למשל: יחידת גמול = 112 שעות, 1.2% ליחידה, תקרה שנתית = יחידה 1) יושבים בטבלת `rule_parameters`, עם `valid_from`/`valid_to` בדיוק כמו לחוקים עצמם. זה שונה מלשמור את **התנאי** (מי זכאי לאיזה ערך) ב-DB — התנאי נשאר קוד. כך אפשר לעדכן מספר (למשל אם האחוז משתנה בהסכם חדש) בלי לגעת ב-`engine.py`, בלי לוותר על הבטיחות של לוגיקה בקוד רגיל.

## התקנה

הפרויקט רץ מול PostgreSQL (למשל DB חינמי ב-[Supabase](https://supabase.com)).

1. `pip install -r requirements.txt`
2. יצירת קובץ `db.env` (לא נכנס ל-git) בתיקיית הפרויקט, עם שורה אחת:
   ```
   DATABASE_URL=postgresql://user:password@host:port/dbname
   ```
   ב-Supabase — Settings → Database → Connection string → **Session pooler** (לא "Direct connection"; לרוב לא זמין ל-IPv4).
3. בשרת (Render → Environment) מגדירים גם:
   - `ADMIN_PASSWORD` — סיסמת הכניסה לממשק הניהול. בלעדיה ממשק הניהול נעול לגמרי (חוץ מהרצה מקומית ב-localhost, שם הוא פתוח לפיתוח). הקישורים האישיים של המורים (`/my/...`) לא דורשים סיסמה.
   - `SECRET_KEY` — מחרוזת אקראית ארוכה לחתימת ה-session.

## איך להריץ

```bash
cd salary_engine
python3 example_run.py
```

זה מאתחל את הטבלאות ב-DB (`init_db(reset=True)`), מזין מורה לדוגמה, ומדפיס תוצאה מלאה + trace.

**שימי לב:** `reset=True` מוחק את כל הטבלאות (כולל מורים אמיתיים שהוזנו!) ובונה מחדש. להרצת השרת הרגילה (`python3 app.py`) זה לא קורה — שם `init_db(reset=False)` רק מוודא שהטבלאות/החוקים/הפרמטרים קיימים, בלי למחוק נתונים.

## מה חסר / שלבים הבאים מומלצים

1. **הרחבה לנושאי שכר נוספים** — כרגע ממומש רק "גמול השתלמות" (סעיף 18). באותה ארכיטקטורה בדיוק אפשר להוסיף מודולים ל: תוספת עוז לתמורה (סעיף 16), גמולי תפקיד (סעיף 17), דרגות קידום (סעיף 20) וכו' — כל אחד כטבלת `rules` + פונקציית `compute_...` נפרדת, עם `topic` משלו.
2. **בדיקות (tests)** — כדאי לכתוב `pytest` עם כמה תרחישי קצה: מורה בלי שבתון, מורה עם 2 שנות שבתון רצופות, מורה שחצה את התקרה, מורה גמלאי. זה הכי חשוב לפני שסומכים על התוצאות בפועל.
3. **ולידציה של קלט** — כרגע אין בדיקה שהתאריכים הגיוניים, שאין כפילויות קורסים וכו'. שווה להוסיף שכבת validation לפני הכנסה ל-DB.
4. **ממשק** — ממשק ווב (`app.py`, Flask) להזנת מורים/קורסים/סטטוס תעסוקתי והרצת החישוב, מול PostgreSQL. כל מורה מקבל גם קישור אישי (`/my/<token>`, ללא login) שמאפשר רק הוספת נתונים/הרצה/צפייה בתוצאה — לא עריכת פרופיל ולא מחיקה. **חשוב:** זו לא אבטחה אמיתית — כל מי שמחזיק בקישור יכול לגשת, זה רק "unlisted URL".
5. **`is_active_teacher` לא בשימוש** — השדה נאסף בטופס אבל לא משפיע על שום חישוב היום (רק `is_pensioner` כן, ב-R15). צריך להחליט: האם מורה לא-פעילה אמורה להיות זכאית לגמול בכלל?
6. **אימות מול מקור אנושי** — לפני הפעלה בפועל על שכר אמיתי, חובה שעורך/ת דין עבודה או אחראי/ת שכר יאמתו את הלוגיקה **וגם את הציטוטים** (`source_doc`/`source_ref` בכל 18 החוקים) מול ההסכם המלא (כולל הנספחים שעדיין לא נותחו במלואם) — זה כלי עזר לחישוב, לא תחליף לאישור מקצועי.
